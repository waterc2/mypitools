# Agent working rules

Cross-project workflow lives here. Repository instructions add project constraints, commands and guide mappings rather than copying this policy.

## Execution

- Stay in scope; consult the relevant project guide before changing its area. Skills/guides are on-demand: reuse unchanged content already in context, reloading only after changes or context loss.
- Call available tools directly for reads, searches and edits. Independent calls may run in parallel; sequential direct calls are fine. Prefer deterministic scripts for mechanical derivations, not as a replacement for source lookup tools.
- Never treat truncated/paginated output as complete data. Continue, narrow the query, or parse the full file in an execution tool and return only needed fields.
- Verify persisted edits with a diff or checksum; preserve pre-existing changes.
- After two failed attempts at the same edit/command without new evidence, inspect the failure and change approach or report the blocker; do not expand scope.

## Code retrieval

When `code_*` tools are declared, choose by the question, not by habit or a tool-use quota:

- Unknown implementation/location → `code_search`. Already know an identifier? Search that identifier alone; otherwise start with core domain terms. Set `path` only when source, search results or the task establish the area; for unknown cross-layer behavior omit it or use `src`, not a guessed layer. If leads are irrelevant, use scoped native lookup directly or optionally refine at most once with an identifier/evidence-backed path, preserving scope. Ranking is not task relevance; use read/trace only for relevant candidates, not automatically the first result.
- Who calls a known symbol / what it calls → `code_trace` FIRST; do not preemptively grep its name because it might be dynamic. Supplement for actual gaps, dynamic registration or test calls after inspecting the trace. Trace targets are symbols/QNs, not file:line. Bounded static connectivity is not runtime/dataflow proof or an exhaustive absence check; field writes and dynamic registries still need source/literal evidence. Compare backend totals only within identical direction/depth/test-filter/dedup scopes.
- Known file / understand implementation, branches or policy comments / exact evidence / edit context → `read` or `code_read`. Reading is not restricted to preparing edits. Continue with `offset`/`limit` instead of assembling a function from repeated large grep contexts; use file:line plus `limit`, not file:start-end. For symbol reads, `before_lines` optionally includes preceding context within the same total `limit`; explicit offsets/file targets are unchanged. Prefer a known path after edits because indexed positions may lag.
- Exact fields/assignments/assertions/copy/JSON/SQL/config → scoped native `grep` for literal locations or expressions; small context may disambiguate a match. This does not authorize tracing an entire persistence chain with repeated context greps: use read/code_read for known function bodies/branches/policy and code_trace for known-symbol relations. No ceremonial graph call before a literal lookup. `grep.path` accepts one file/directory, not a path list; separate independent paths may be queried in parallel. A capped grep is not exhaustive. Tests may be read/searched directly; test helpers and existing assertions are not production proof or current requirements.
- Discovery is staged: inspect search/trace results before choosing a fallback. Do not batch discovery with speculative grep for the same question; parallelize independent questions only. For irrelevant/incomplete results, use bounded native lookup directly or optionally refine at most once by identifier/evidence-backed path, preserving scope; a retry is not required. Never repeat an unchanged probe or infer absence from a miss.
- The code tools need no discovery, skill load or project/schema parameters. Prefer English identifiers/keywords; mixed queries use existing English tokens. For `needs_english_rewrite`, use scoped native lookup directly or optionally rewrite into English at most once with the same scope; do not repeat pure Chinese or trust nonempty semantic candidates. Exact Chinese copy uses native grep.
- Search defaults to locations; optional `preview_lines: 1..32` and indexed signatures are navigation, not exact-text/Edit evidence. Use read/code_read for current source. A `Text fallback` is literal search, not semantic evidence. Search defaults to `scope: "implementation"` (test paths excluded); use `"tests"` for test discovery or `"all"` for both. A test `path` does not override scope. Filtering is path-based within at most 48 candidates per executed stage, not full-index exclusion; incomplete windows cannot support absence claims. code_trace still excludes tests; consult current declarations for tool bounds.
- Load the codebase-memory skill only for advanced graph queries, impact/coverage audits or missing simplified tools. For paging/custom depth, discover the original MCP tool with `tool_search`, wait for its declaration, then follow that schema. Rediscover missing tools after reload; historical calls do not prove availability. Use actual structured tool calls, never textual/XML imitations. Do not mix wrapper parameters/directions with raw MCP schemas, assume aliases or enable hidden/disabled tools. If graph access is inconclusive, use source and disclose the limit.
- This source-lookup routing takes precedence over generic context-mode/ctx_* batching or file-analysis advice. Those tools remain useful for large logs/data, stored knowledge and unrelated command output. `bash` is for git/build/tests; `find`/`ls` locate paths. Do not use shell grep/sed/cat loops or node probes to retrieve source. If `code_*` is absent, use the project's declared tools instead of assuming availability.

## Verification

- Select the smallest sufficient checks from this task's changes, not the whole dirty tree. Use source/dependencies and relevant graph impact where useful; cover affected boundaries without an arbitrary file cap. Review shared setup, dynamic loading, fixtures, DB/content and broad contracts when selecting tests. Before execution, name affected behavior and exact commands/test files; honor stricter project rules.
- Full/broad suites, domain-wide checks, unfiltered watch and E2E require explicit approval, including through wrappers. Completion/commit preparation, no matches and failures never authorize broader checks. If necessary scope is broad or unclear, explain and ask.
- Batch coherent edits, then one final targeted pass. Intermediate checks need a concrete diagnostic question; do not rerun for status updates or commit preparation. Reuse passes only while relevant source, tests, fixtures, config, dependencies and generated inputs are unchanged; unrelated docs/status changes do not invalidate them.
- Diagnose failures before rerunning only failing/newly affected scope after a fix. After two consecutive failures in that scope, stop automatic retries; proceed only with new evidence or user direction.
- Docs/comments/copy-only translations/static styling or assets need relevant diff, references or visual checks, not runtime suites, unless a project-specific check applies.
- Preserve assertions, isolation, timeouts and safety gates. Record command, scope and result; report unrun checks/risks, never weaken checks or imply broader verification.
