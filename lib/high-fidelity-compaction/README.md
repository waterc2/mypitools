# High-fidelity compaction for Pi

This personal extension replaces `extensions/compaction-model.ts`; its pure engine is `lib/high-fidelity-compaction/core.ts`, with deterministic preservation/budget helpers in `preservation.ts`, source-grounded coverage review and state navigation in `coverage.ts`, and balanced/source-backed retention in `retention.ts`. It adds no model-callable memory tools and makes no background requests. Summary work runs only when Pi asks to compact. Reload Pi with `/reload` after installation; `/compaction-model` shows config and the latest successful audit.

## Retention semantics

Plugin version **v6** treats `targetRetention: 0.5` as a source-backed target for the **estimated total resulting context** (system/tool prompt, verbatim retained recent history, generated checkpoint and supplemental original evidence). Allowed targets are 0.4–0.7; 0.4 is the reported minimum. Short generated text no longer silently wastes the rest of the budget: distinct, attributed source fragments are selected to approach the target without more model calls. If unique source content is exhausted or safety headroom prevents the minimum, the audit and notification explicitly report a shortfall rather than padding or declaring success at 40%.

Planning normally counts the finalized pre-compaction projection and retained messages using the **same** conservative ASCII/3 + non-ASCII*2 estimator used for the result. If Pi's prepared `tokensBefore` is larger, it is used as an explicitly labelled upper-bound baseline, never presented as a tokenizer measurement. This fixes the old mixed-metric retention calculation. `maxRetention` and `continuationReserveTokens` remain upper safety gates. Provider tokenization may differ significantly: neither 40–70% actual provider-token retention nor semantic recall can be guaranteed without a trusted tokenizer. A metadata-only observer records the first successful same-model request after compaction, including cached input and excluding output, separately from host estimates. The pre-compaction reference is the latest available same-model input usage, not necessarily the final overflowing request; request hooks/queued inputs may differ. Incorrect model limits in `models.json` must be corrected separately by the user; this plugin does not change them.

Pi's canonical `firstKeptEntryId` is preserved. The plugin does not change **when** compaction triggers: automatic thresholds, overflow/length recovery decisions and manual `/compact` remain owned by Pi. It does not change `reserveTokens`, `keepRecentTokens` or model context-window settings, change the main model, delete the original journal or inject state after each turn. Context edits/omitted attempts are respected through the projected preparation; no abandoned branch is resurrected. If retained history/system already consumes the requested budget, compaction is cancelled with a diagnostic, rather than throwing away additional recent history.

## More input, more output

- Default summarizer remains `mytoken/gpt-6-luna`, thinking high.
- Per-request input ceiling: 160,000 estimated tokens, further bounded by the summarizer's context/output limits and safety reserve.
- Per-request output ceiling: 32,768 provider tokens, further bounded by the model. Text has a separate safety budget; output capacity includes room for reasoning. Initial detail targets use 82% of allocated text capacity, then adapt within the same compaction using observed host-text/target ratios (20–92%, not provider usage). Unused capacity rolls to later parts; no padding or extra calls just to fill a quota. There is no trusted tokenizer for this custom model on this installation, so the conservative estimator remains authoritative rather than guessing a model encoding.
- The actual joined input determines whether one request fits. Multi-part input is balanced, including explicitly marked source-record splits when needed, instead of moving an entire final message into a tiny second call. Up to 75% of the checkpoint text budget is assigned to generated/detail sections; the rest is reserved for distinct original evidence, so extra model calls are not purchased merely to fill unused capacity.
- Chronological parts receive a minimum allocation and then weighted detail capacity: visible user requests/constraints, explicit candidate/verification records, next actions and tool-result signals have higher priority. Length contributes sublinearly so a long repetitive log does not automatically dominate short constraints. Original serialized input is still supplied in chronological order, not discarded by this weighting.
- A normally completed, structured response that exceeds its allocated text budget or changes a narrowly recognized explicit status may be rewritten **once total per part** from the same original part, with a smaller detail target. No tail slicing, excerpting of generated summaries or relaxed budget checks. The rejected text is not fed back as history. Partial, empty, malformed, tool-calling or failed provider responses are still rejected immediately.
- Each nested summary request uses a fresh session/routing ID and exactly one supplied prompt, with no main-conversation history or transport session reuse. Pi applies a successful checkpoint through its own projection replacement; keeping raw journal entries on disk does not mean sending them again.
- Tool output reaches the summarizer **whole** (no per-result 16,000-character cutoff). Complete visible records are split across input parts under one request budget, and each review sees its full assigned part. Data already truncated by a tool, provider, output guard, or other extension cannot be recovered; image bytes are never replayed.
- `toolResultMaxChars` now bounds only the small host evidence preview, not the actual summarizer input.
- Short/no-text assistant responses may contribute bounded working-note excerpts (1,800 characters each), explicitly UNVERIFIED. Opaque signatures and image bytes are not sent. Set `thinkingMaxChars: 0` to omit working notes entirely. Treating notes as evidence is prohibited.
- Previous checkpoint and both ordinary/split-turn messages share the same detailed schema: binding constraints, facts, decisions/candidates (confirmed/ruled out/unresolved), verification ledger, precise remaining actions, evidence limits.
- When input or desired output exceeds one request, chronological parts are generated and joined, **not recursively summarized again**. Later evidence supersedes older claims. Large previous checkpoints are likewise partitioned, not silently chopped. Parts are not a global semantic reconciliation, so contradictory legacy material can remain explicitly chronological; the bounded current-state navigation and full-source review reduce, but do not eliminate, that risk.
- A small host-preserved evidence appendix retains key tool-result lines even if the model omits them. Exact repeated signal lines are deduplicated within a result; associated tool-call commands are retained when the call is present in this summarized span. It is bounded and labelled incomplete, not a substitute for full original logs.
- A host-preserved critical-record block uses at most 16% of the summary budget, capped at 5,000 estimated tokens. It retains whole visible-prose source lines with source labels, prioritizing user constraints, goals/next actions, and explicitly identified reports. Exact duplicates are removed; oversized or excess records are omitted with a count, never cut into misleading fragments. Fenced/indented code, block quotes, tool results and working notes do not become critical records. The block is carried into successive compactions without repeatedly adding the same source prefix. Historical permissions remain historical DATA, not new instructions.
- For narrow candidate syntax (`R1 RULED OUT`, `UNRESOLVED R2`) and explicitly identified checks (`CHECK[command + files + revision]: FAIL`), the protection block keeps the latest explicit report per identifier. This is an index of **reported states**, not semantic reconciliation or host-verified truth. Reusing IDs for unrelated work is ambiguous; use distinct check IDs for different scopes/revisions. Incompatible or unsupported explicit states in generated text fail that part's review; literal and semantic checks remain separate.
- Every generated part gets a **source-grounded coverage review**: a second call sees the full assigned source plus the draft and returns strict JSON omissions/contradictions that must quote exact source substrings. Exact missing explicit reports are also checked deterministically. A problem triggers at most one full rewrite from the original part, then a second review. Unresolved problems cancel the compaction; no unreviewed part is accepted, truncated, or silently dropped. Review calls are included in `maxCalls`, so each part needs at least two slots.
- A **source ledger** keeps exact user constraints, goals, next actions and explicit reports with stable fact IDs and source entry IDs. It is stored in `details.highFidelityLedger`, outside model context, and re-enters later compactions as immutable historical evidence; semantic corrections stay chronological rather than rewriting old quotes.
- A **current-state navigation** block indexes only the latest explicit candidate/check reports by source order, and is bounded or fails closed rather than omitting a latest report. It is not a global semantic reconciliation: natural-language permissions, older chronological parts and kept recent messages still matter and later messages may supersede the index.
- After generation, unused checkpoint capacity is filled with prioritized, source-labelled original fragments, selected chronologically within the final appendix. Exact repeated substantial lines/fragments and already-covered lines are deduplicated. Tiny fragments are not used as padding. Serialized source labels, UTF-16 offsets and `partial` markers disclose fragment boundaries; this is historical untrusted DATA, not new instructions or host-verified facts. Optional assistant working notes, opaque signatures and image bytes are never copied into this supplement. The plugin itself applies no per-tool-result cutoff; material already omitted upstream (tool limits, output guard, provider truncation) cannot be recovered. Subsequent compactions unpack the source block instead of quoting its JSON recursively. No additional model calls are made for supplementation.
- Up to 16 calls per compaction by default, **including coverage reviews and every rewrite**. Every chronological part reserves both a generation and a review slot; repairs cannot consume them. If the work cannot fit those budgets, fail clearly instead of silently dropping middle parts or accepting unreviewed text. With many large parts, the default may legitimately cancel — raise `maxInputTokens`/part size or `maxCalls` explicitly, or keep `fallback: "cancel"` for fidelity.

## Config

Edit `~/.pi/agent/compaction-model.json`. Existing keys remain supported. Unknown extra keys are ignored; invalid known values cancel compaction with a diagnostic. Missing config uses defaults.

```json
{
  "enabled": true,
  "model": "mytoken/gpt-6-luna",
  "thinkingLevel": "high",
  "applyToBranchSummaries": true,
  "targetRetention": 0.5,
  "maxRetention": 0.7,
  "maxInputTokens": 160000,
  "maxOutputTokens": 32768,
  "inputSafetyTokens": 8192,
  "continuationReserveTokens": 32768,
  "toolResultMaxChars": 16000,
  "thinkingMaxChars": 1800,
  "evidenceMaxTokens": 5000,
  "maxCalls": 16,
  "fallback": "cancel"
}
```

`fallback: "cancel"` is deliberate: provider errors and empty/partial/tool-calling summaries never replace history. Over-budget text also cannot replace history: only a complete, structured, in-budget part that passes both its exact-report check and a full-source coverage review can be accepted; failure after the single rewrite (or no remaining call capacity) cancels with measured bounds or source-grounded issue count. Pi may report cancelled compaction or need user intervention at a full context; there is no unbounded retry loop. If you prefer availability over fidelity, explicitly choose `"native"`: the plugin audits the failure and returns control to Pi's native, lower-fidelity summarizer. An aborted signal always cancels, never triggers fallback.

`applyToBranchSummaries` preserves the previous `/tree` model override using Pi's native branch-summary implementation. **The high-fidelity serializer/retention target applies to compaction, not `/tree`.** Branch summaries still use native evidence selection.

## Verification gates and residual limits

Coverage review checks omission and contradiction against one assigned part. It does **not** prove semantic completeness, global consistency, or that a fact is true. Reviewer quotes are validated against the source, but a model can still miss a real omission, and reported issues need a repair and a passing re-review. Deterministic literal lists are advisory. Stable IDs come only from canonical projected entries; unmapped messages are labelled `message-N` and counted in the audit. `highFidelity`/`highFidelityLedger` come from the same extension result; a hand-written session entry could supply arbitrary ledger JSON. Provider errors, aborts and malformed reviews still follow `fallback`.

## Audit and privacy

Successful compactions store `details.highFidelity`: requested/actual models, fallback=false, trigger, target and estimated actual retention, split-turn flag, part count, budget estimates, excerpted working-note characters, coverage-review counts/detected issues, state-navigation and ledger counts, provenance mapping counts, and estimator name. Audit version 6 distinguishes total `calls`, chronological `parts`, `budgetRewrites`, `integrityRewrites` and `coverageRewrites`. `allocation` records the generated-text budget, input-part sizes, per-part ceilings, per-attempt targets and final summary-budget utilization. `retention` records its basis, before/after estimates, ratio, minimum/target status, shortfall reason and source-supplement statistics. `tokensBefore` is still Pi's original value; it is not silently replaced. `projectionEstimateBefore` and `planningBasis` explain which planning baseline was selected. `preservation` reports selected/omitted critical-record counts, duplicates and detected explicit-status conflicts, plus the semantic-coverage limitation. Successful compaction usage includes rejected attempts that led to an accepted rewrite. Cumulative read/modified file lists stay in `details` across plugin-written compactions.

The notification and `/compaction-model` show the loaded plugin version, making stale v3/v4 processes visible. After the first successful same-model main request, `high-fidelity-retention-observed` records observed before/after input totals and ratio (or null when no valid baseline is available). This observer only appends metadata excluded from model context; it does not change messages, settings, triggers, retries or invoke models. A `/reload` or restart is still required in every already-running Pi process.

Failures append metadata-only `high-fidelity-compaction-failure` entries, including any actual returned model and attempted usage. These entries do not enter main-model context. Failed-attempt usage is recorded there but is **not included in Pi's session token/cost totals**; successful multi-call usage is summed into the compaction entry. Audits contain no full prompts or raw working notes.

The configured summarizer receives more conversation/code/tool evidence and optional readable working notes than native compaction. Ensure that endpoint is trusted. This plugin uses Pi's registry/authentication, not raw fetch or credential logging; it cannot promise third-party privacy filters apply to nested requests. Tool/transcript text is untrusted data, not instructions. No real service handles or databases are opened.

## Verification

Run only this extension's isolated tests and type check (add `coverage.ts` to `tsconfig.json` if the type check should include it directly; it is imported by `core.ts`):

```sh
node --experimental-strip-types --test /home/brady/.pi/agent/lib/high-fidelity-compaction/core.test.mjs /home/brady/.pi/agent/lib/high-fidelity-compaction/extension.test.mjs /home/brady/.pi/agent/lib/high-fidelity-compaction/budget.test.mjs /home/brady/.pi/agent/lib/high-fidelity-compaction/quality.test.mjs /home/brady/.pi/agent/lib/high-fidelity-compaction/retention.test.mjs /home/brady/.pi/agent/lib/high-fidelity-compaction/v6.test.mjs
node /home/brady/code/cardsearch/node_modules/typescript/bin/tsc -p /home/brady/.pi/agent/lib/high-fidelity-compaction/tsconfig.json
```

The test harness uses the installed Pi loader/types and mock responses; no live model calls, session writes or DB writes. The tsconfig's Pi declaration path and test loader are specific to this machine. No full game suite is needed or implied. Pre-v6 generation fixtures use `testCompletion.mjs` to return an explicit clean review. `v6.test.mjs` covers full tool text, review repair/failure, provenance, ledger stability, current-state navigation, malformed reviews, call reservations and extension persistence. `quality.test.mjs` is a fixed offline regression corpus covering Chinese constraints, successive checkpoints, rejected candidates, scope-labelled check status, command/evidence association, omissions and bounded failure paths. It mocks generated replies (including intentionally wrong ones); it is NOT a real-model quality benchmark. Production semantic recall/ratio require separately approved, privacy-reviewed model evaluation; deterministic tests cannot guarantee those.
